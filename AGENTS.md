# Trackwise

A small team's tracker for tasks and goals: who owns what, where it stopped, what happens next. Intent is in `docs/BRIEF.md`; every build decision is locked in `docs/PLAN.md` (stack, routes, roles, schema, design tokens, steps). Follow the plan; if something in it is impossible, say so instead of choosing differently. The team's conventions are the Apex skills (`apex-architecture`, `apex-ui`, `apex-ux`, `apex-planning`); the reference implementation of the same conventions is the Clarity project at `C:\Users\max\clarity`.

- Next.js 16.4.1 with `cacheComponents` and `partialPrefetching` on. Session reads sit behind `<Suspense>` (each `(app)` page has a `loading.tsx`); never `use cache` task, goal or proposal data.
- Data access goes through `lib/dal/*` with a `Viewer` (`lib/viewer.ts`), scoped by `org_id` in SQL. Permissions are pure predicates in `lib/permissions.ts` (unit-tested). Mutations are server actions in `actions/`: zod parse → `requireViewer` → permission → transaction → `ActionResult` (`lib/action-result.ts`).
- Schema: `db/schema.ts`, applied with `npm run db:push` (no migrations folder; additive changes only once real data exists). The one breaking change, 2026-11-03's funnel, has its own script: `npm run db:backup` then `npm run db:migrate-hierarchy` then `npm run db:push` (docs/RUNBOOK.md).
- Checks before calling anything done: `npm run typecheck` (runs `next typegen` first), `npm run lint`, `npm run test:unit`, `npm run build`, and the relevant walkthrough.
- Hosting: the team VPS runs it under pm2 on port 3015 (`ecosystem.config.js`, `deploy.sh`, run by the owner); the database is Postgres (Neon), reached through `DATABASE_URL`. Never deploy or push unless asked. Environment variables are listed in `.env.example`. The team's delivery workflow (owner-approved Trackwise tasks, PR-only `main`, environments, schema-change rules) is in `docs/WORKFLOW.md`.
- Roles are per workspace: `admin`, `leader`, `member`, `stakeholder`. The people in a workspace are its **members**. Stakeholders see Home · Goals · Proposals · Reports (the Executive view only). **The funnel (docs/PLAN.md, 2026-11-03 log): a workspace holds projects; every goal belongs to one project (`goals.project_id`; a sub-goal is in its parent's project, one level deep, its target never past the parent's); a task belongs to a goal (and so to that goal's project), to a project alone, or to nothing.** There are no teams and no requests any more.
- Assignment is a set of people: `task_assignees`, no owner.
- **One project picker** in the navigation (cookie `trackwise.project`, `lib/project-scope.ts`) narrows the List, Board, Home, My Work, Goals, Proposals and Reports screens and the add bar's default project. There are no per-page project pickers. The same component (`components/projects/project-picker.tsx`: search, **pinned** projects first in the person's order (`project_pins`), then this browser's recents) is every form's project control, and `components/goals/goal-picker.tsx` is every goal control (picking a goal sets the project).
- **One set of task statuses** everywhere (`TASK_STATUSES`): the Update progress form's Status control offers them (Blocked asks for the reason, Awaiting approval for the approver, Completed for a summary, Rejected for a reason); there is no separate "Mark as".
- A comment on a task is **open until someone resolves it** (`task_updates.resolved_at`), and a task cannot be completed or approved while a comment is open (`lib/tasks/transitions.ts`); every form says so before the save.
- **Repeats** (`lib/recurrence.ts`): a task may repeat (every N days / weeks on chosen weekdays / months, at a time of day, until an end date); completing the latest occurrence makes the next one, never doubled, and `catchUpRecurrences` (`lib/dal/recurrence.ts`, called at the top of every work screen) writes the occurrences a missed series owes up to today. A goal may repeat the same way; its next occurrence gets fresh copies of its tasks.
- **Proposals** (`lib/approvals/policy.ts`, `lib/dal/approvals.ts`, `actions/proposals.ts`): a new task is a proposal when its goal or project has sign-off on (the **Sign-off** dialog on their pages: an ordered chain, a bypass list) or a stakeholder adds it; the chain is copied onto the task (`task_approvals`), each step signs or declines with a note, the last signature makes it live. A pending proposal shows in the lists at once, tinted and chipped "Waiting for sign-off" (`visibleWork`); a declined one shows to its proposer; counts, progress and reports keep to live work (`liveOnly`). A decision carries the `updatedAt` the decider saw and is refused if the task changed since. A step may name several people (any one signs); `/proposals` lists them (Waiting for you · on others · Proposed by you · Decided lately).
- **Several tasks at once**: rows tick on the List tab, My Work and the project and goal pages (`components/tasks/selection.tsx`); the bar sets a status, assigns, moves or deletes, one transaction per task, and names the ones that couldn't.
- **Goals**: every goal has an "Everything completed" task (`tasks.goal_closer`, `lib/dal/goal-closers.ts`): refused while other tasks under the goal are open, it marks the goal achieved when completed last; only admins, leaders and stakeholders use the goal page's own Mark completed; leaders and admins may delete a goal (its tasks stay in the project; its sub-goals become top-level, or go too when asked); a goal past its target that isn't completed shouts (red strip, red cards, a Home banner). `/goals` has a List view (soonest first, open tasks under each goal, sub-goals nested) and a **Branches** view (`lib/goals/graph.ts`, `components/goals/goal-graph.tsx`: cards on a scrolling canvas, arrows for `goal_links`, dashed for sub-goals; managers drag a card's dot onto another card to link, × on an arrow to unlink); a goal page's Connections card sets what it comes after and leads to (no loops).
- What exists: sign-in (Google + magic link), workspaces with onboarding (skippable), invitations, members and roles, profile and email preferences; tasks with the Resume card, one-form Update progress, status transitions with append-only history, comments with Resolve / Reopen, list and board views with URL filters that show when they are on (tinted controls, a "Filtered:" chip row, Clear all, a **Dates** range on the created / completed / updated date, also on My Work; the board's cards drag between columns) living as tabs on `/home` (`?view=list|board|projects|home|draft`; the **Draft** tab is a notepad saved per person (`drafts`) with "Turn into work" (the capture helper) and a floating copy that follows you around the app; the tabs drag to reorder, the first tab is the landing, kept in the `trackwise.homeTabs` cookie), **rows that expand in place** (the title links to the task; the rest of the row opens the description, people, place, due, repeat and latest progress), the add bar (`components/tasks/quick-add-task.tsx`; priority, due, project, goal once a project is chosen, assignees; `!high` `@tomorrow` `@sam` shortcuts in `lib/tasks/quick-add.ts`; N focuses it, More options opens the full dialog with time, repeat, next action and description), the ⌘K palette (title **and description** search, a Recent list, "See every task matching…") and N/U shortcuts; projects with their goals and tasks; goals with sub-goals, connections and real progress; the Members page; role-aware Home (proposals waiting for you, goals past their target); in-app notifications with email by preference; Reports (Executive health · Workload · My work; presets plus Custom; the Executive view is verdict → chart → Decisions waiting (approvals and pending proposals) → health board → Stalled → People; the chart's y axis is activity per day with one fixed block per task and a strong Today line; print and CSV). **Capture from a meeting** lives on the Draft tab (`/capture` redirects there; leaders and admins): jot or upload notes, review the drafted project, its goals and tasks, create what is ticked. The button explains itself until `ANTHROPIC_API_KEY` is set.
- Character counters appear only in the last fifth of a field's cap, as "N left" (`components/character-counter.tsx`); the caps live in `lib/limits.ts` and the server enforces them (`lib/sanitize.ts`).
- In a `sql` fragment, a correlated reference to the outer row is written `${tasks}.id` (the table, then the column), never `${tasks.id}`: a select from one table renders the latter as a bare `"id"`, which the subquery's own table captures, so the count comes back 0 and the people come back empty (found 2026-11-03 in the status dialog's open-comment hold; a unit test renders the fragments to check).
- Turbopack sometimes keeps a stale server module graph after a new export is added to an existing module ("`x` is not a function" at runtime although typecheck passes). Restart the dev server (delete `.next/dev` first) before concluding anything.

- **Sign in:** `GET /api/test-login?as=<persona>&secret=<TEST_MODE_SECRET>&to=/home` on a dev server. Port **3015** is the owner's own `npm run dev`; it reloads your edits live, so use it (`--base=http://localhost:3015` / `TEST_BASE_URL=http://localhost:3015`). Next 16.4 refuses a second `next dev` in the same directory ("Another next dev server is already running"), so you can only run your own when 3015 is free: `BETTER_AUTH_URL=http://localhost:3021 npx next dev --port 3021` **with a matching `BETTER_AUTH_URL`**, because Better Auth redirects (sign-out, magic links) go to `BETTER_AUTH_URL`. The secret is in `.env.local`: **do not read `.env*` yourself** (denied in `.claude/settings.json`); the scripts pick it up. Rules and guards are in `lib/test-mode.ts`: dev builds only (a production build answers 404), timing-safe secret check, only these personas. It inserts a 12-hour database session plus the `better-auth.session_token` cookie, and sets the persona's workspace as active.
- **Accounts:** `npm run test:seed` (create / reset, rewrite `docs/TEST-ACCOUNTS.md`), `npm run test:status`, `npm run test:tidy` (put both workspaces back to the seeded state, remove workspaces a run created), `npm run test:clean` (delete both workspaces and every `.test` account).
- **See a screen:** `node scripts/test-browser.mjs <persona|public> [path] [--width=390 --height=844 --dark --full --base=…]` signs in with headless Chrome, prints horizontal overflow and console errors, and saves a PNG to `.test-shots/` (git-ignored). **Read the PNG to look at it.** Check phone (390×844) and desktop (1280×900), light and dark.
- **Run a whole flow:** `npm run test:walk` runs everything in `scripts/test-walkthrough/` and sums up; each script also runs alone and takes `--only=` to pick a part. `01-sign-in` (every persona lands on `/home` with the right navigation; history lists every event) · `04-proposals` (a stakeholder proposes → declined with a note → sent again → approved → live; Lumen Health's two-step chain; the bypass list) · `05-roles` (what each role may not do; reopen; the audit trail) · `10-reports` (the Executive verdict first, then the activity-axis chart with its Today line, decisions and the health board against the database; the navigation's project picker across sections and CSV links; a member's phone view) · `11-capture` (notes to a draft, edit and untick, create, then the tasks, goal, history note and notification in the database; who is turned away; where it is offered; the review on a phone) · `12-repeats` (the daily task's next occurrence, never doubled; one Status control; the weekly goal's next week with copied tasks; who may complete a goal) · `13-pickers-and-batches` (pins and search in the project picker, the goal picker following the project, two tasks changed from the selection bar and the comments hold naming the refused one, drag-to-link and × on the canvas with a loop refused, deleting a goal that keeps its task, a stakeholder's Home and Executive report) · `14-drafts-closers-and-chains` (the Draft tab saving itself and the floating notepad across pages, a proposal visible at once in the list and My Work, a stale decision refused, the closer refused early and achieving the goal last, missed repeats caught up within the end date, a sign-off step naming two people, deleting a goal with its sub-goals). To write another, import from `scripts/test-walkthrough/lib.mjs`.
- **Pickers in walkthroughs:** the assignees picker is a button that opens a searchable list of people; click the button by its text ("Unassigned", "You") or its label ("Assigned to"), click names inside `[cmdk-list]`, then press Escape. It is disabled until its options load, and `click` keeps trying until then. The project and goal pickers are command lists: `pickChoice(browser, "[data-project-scope]" | "#quick-add-project" | "#task-goal" …, <row text>, { search })` from `lib.mjs` (search "" for "All projects" / "No project"); `pickedValue(browser, selector)` reads a trigger's `data-value`.
- **Scope to the thing you mean.** Settings lists every member at once, so a page-wide `click("Remove")` presses the first row's button. `near: "Sam Dev"` keeps a click or a check inside that row.
- **Email:** nothing is ever sent to a `.test` address (`lib/mail`). In development a magic link, invitation or notification email to a `.test` address is printed to the dev server log instead, so the real email sign-in can be followed too. Notification emails follow each person's preferences (Settings) and are sent after the response with `after()`.
- **AI:** a `.test` persona never reaches the model. On `/capture` they get the plain parser in `lib/capture/fake.ts` (lines starting with `Meeting:`, `Project:`, `Goal:`, `Action item:`), so no walkthrough spends money or sends a transcript anywhere; a real account needs `ANTHROPIC_API_KEY` (unset = the page says it is not switched on).

## Ground rules for test runs

- The scripts only ever reset or delete workspaces whose **every** member is a `.test` account, and refuse to touch a seeded slug that has a real member. Never sign in as, or act on, a non-test account.
- Leave things tidy: `npm run test:tidy` after a run (`npm run test:walk` does it itself).
- Port 3015 may be the owner's own `npm run dev`. Check who owns it before stopping anything; if it is theirs, use it and leave it running.
- This is Chrome emulating a phone. Real iPhone / Android behaviour (keyboard, safe areas, touch scrolling) is not proven by it; say so.
